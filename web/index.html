Amber

One memory across every agent.

Memory that doesn't rot.

Every session, your coding agent starts from zero — so you explain your project again. Amber is reviewed memory: it learns from your sessions, you approve what it keeps, and everything lives in one local SQLite file you own. No Docker, no API key, no account.

The problem

Groundhog Day. Your agent forgets everything between sessions.

The stack, the conventions, the decision you explained on Tuesday — gone. You repeat yourself, session after session, and pay tokens to do it.

Rot. The DIY fix — a fat CLAUDE.md — backfires.

The file grows into hundreds of lines of stale facts and contradictions nobody audits, injected into every prompt. Put to the test, this practice often fails to improve task success while raising cost — and machine-generated context files can make results actively worse (the evidence).

The black box. Vendor auto-memory isn't yours.

It quietly writes things about you and your codebase into a store you can't fully read, export, or audit — locked to one tool. And anything the agent reads (tool output, a web page) can write into what it believes.

Instructions are what you tell an agent (CLAUDE.md).
Memory is what it learns (Amber) — reviewed by you.

Two minutes to your first memory

amber init
amber remember "We deploy billing to Fly.io on Fridays" --type decision

How it kills each problem

  • forgetting
    A session-start briefing, so you stop re-explaining. Budgeted to ≤700 tokens (~1% of a session), deduped against your CLAUDE.md, framed as data — not instructions.
  • rot
    A review inbox between "the agent said it" and "the agent believes it." Approve, edit, or reject what it learned. Consolidation merges duplicates and retires stale memories from the briefing — never from the store, never by silent deletion.
  • black box
    One SQLite file, readable with any tool. recall --why shows exactly what was injected and why. Export everything to an open format; ingest your existing CLAUDE.md / MEMORY.md in one command.
  • poisoning
    Memory treated as an attack surface. Trust tiers, taint marking, quarantine: content from tool output or web pages never auto-injects until you review it — enforced by a poisoning test suite in CI.

Why a review step

ETH Zurich researchers tested the most common practice — a static context file injected into every prompt — and found it often doesn't improve task success, raises inference cost, and that LLM-generated context files made results worse in most tested settings.

That isn't an argument against memory. It's a measurement of what happens when memory is unreviewed, unbudgeted, and never pruned — the exact failure Amber is built to prevent.

So Amber makes no accuracy promises. It shows its work instead: recall --why lists every injected memory and the reason. If memory isn't earning its tokens in your workflow, Amber is the tool that lets you see that. Read the details →

Four questions to ask any memory tool

  1. Can I see everything it remembers? amber browse
  2. Can I see exactly what it injected, and why? amber recall --why
  3. Does it clean up — merge, resolve, retire — without silently deleting? amber consolidate
  4. Does it keep secrets out? secret + PII scan on write and export
