# Early user acquisition loop

On 2026-07-29, the owner chose to optimize Amber's product and landing page,
then seek actual users. Required calls, interviews, and the preview-only
headline A/B test are deferred. They did not fail; they are not current release
or implementation gates.

## Current objective

Make the product easy for an individual developer to understand, inspect, and
try from source:

1. state the cross-agent, reviewed-memory benefit in the first screen;
2. show real Amber output near the quick start;
3. present one clear local-install path at desktop and mobile page widths;
4. direct interested developers to the source repository; and
5. record adoption signals in dated evidence without turning them into claims.

The current page does not use analytics, a waitlist, or an account system. Do
not create those systems only to produce a metric. GitHub traffic, clones,
stars, issues, discussions, and pull requests can provide directional signals
while GitHub remains the project boundary.

## Evidence rules

- Record volatile observations in a dated file under `docs/evidence/`.
- Keep repository views and clones separate. Clones can include automation and
  are not proof of a person using Amber.
- Do not call traffic, a clone, or a star a user without direct evidence.
- Do not claim product-market fit, launch readiness, or validated demand from
  directional repository signals.
- Collect qualitative feedback asynchronously when actual users volunteer it.
  Calls and formal interviews remain optional unless the owner changes this
  decision.

## When to reconsider

Revisit the acquisition path when real adoption evidence shows a concrete
problem, such as repeated install failure, unclear positioning, or a common
request from active users. A future interview study can help answer a specific
question, but it is not a prerequisite for improving Amber now.
